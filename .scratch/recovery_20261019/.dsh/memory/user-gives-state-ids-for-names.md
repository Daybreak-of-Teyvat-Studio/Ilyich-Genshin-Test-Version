**用户钦定格式规矩（2026-10-04，已写入 skill gamma-pipeline.md）——「数字+名字」按有无括号分流，杜绝省/州语义猜测**：
- `2149烟谜主（25，首都）` = **VP**：括号里必有胜利点数值，可带「首都」标记（同国多首都按指令顺序取最后生效）
- `643圣火竞技场`（无括号）= **state 命名**：只有 id 和名字，且**是州号直给，绝不做"省号→所在州"解析**
- `389胜利点清除` / `1482*`（星号后缀）= **清除该省 VP**（state 条目 + VICTORY_POINTS_<pid> key 都要删）
- 合并语法 `A+B=A`（759 并入 735 写作 `735+759=735（合并，暂时不做）`）

**Why**：2026-10-04 纳塔批次实证——无括号的 12 条州名被当成省号解析（"省号所在州"），名字全挂错州（`643圣火竞技场`→写到 s613 因 p643∈s613），其中 3 个错号还覆盖了已有真名（s110 稻妻城、s595 无郁稠林北、s645【三运河之地】，修复须查批次前备份恢复原值而非一律改回 `*`）；VP 名还错位一格（2149 的名值写到下一项的 389 上）。32 条指令只对 15 条。

**How to apply**：
1. 解析指令先看**有无括号**分流 VP/州名，再看是否带 `*`/「清除」/「首都」标记；不做存在性猜测。
2. 超 state 上限的号（如 1379 > 890）可能是省号语义（p1379 所在州命名），单独跟用户确认。
3. 批次落盘后**逐条对照指令跑审计**（tools/audit_natlan_batch.py 是模板：当前值 vs 批次前备份，区分"从未落实"与"后来丢失"），报 ✓/✗ 清单。
4. **VP 本地化 key 已存在但名字不同 ≠ 冲突**：若指令明确给了新名字（如 p4148「回声之子」→「曜石图腾柱·回声之子」），按改名更新，不要以"防冲突"为名跳过。
5. **用户指令即权威（2026-10-07 实证）**：州名条目=覆盖现值（s708 厅→地、s730 覆盖旧残留名）；VP 括号数值=最终值，现值不同即**改值**（p1137 25→50）；VP key 不同名即**改名**（p763 其三→其一）。同批同一 pid/州号出现两条 → **后者生效**并在报告标出（s577 双名、p3077 双名）；不同州可共用同名（478/463 都叫苔骨荒原，照写）。
6. **`A+B` 默认是转省，不是人工映射**（2026-10-08 实证）：`47+15` = 把省 47 从原州转到 s15（属"正常转省"）——我曾连错两次（判成 beta→gamma 人工映射、又判成"映射指令"），被用户明确纠正"不是映射，是正常的转省"。**只有用户说"迁移/映射"时才当映射**，否则一律按转省执行（含 VP 跟随、buildings 列同步、回读验证）。
7. 旧教训仍有效：历史上（格式规矩之前）我曾把裸数字判成省号、把 p 前缀当州名、把 VP 清除项错位配对——都被用户纠正；被纠正后先全量更正再继续，不辩解。**改正前先把错做的动作从备份还原**（转省类误操作要撤干净再重做，别在上一个错误结果上叠加）。
8. **用户会即时修正自己（10-09 实证）**：先说"应该是和 708 对调吧"（指 750），随即更正"**是 708 和 750，不是 718**"——照最新一条执行即可，别纠结先前那句；用户对自己地图的直觉通常准确（他抓出"750 怎么会是陆地州"就是真问题）。
9. **多做核对优于省步骤**：用户认可"先核对再动手"这种做法（"这里是我之前搞错的地方，你核对一下"）——核对是廉价的，返工是昂贵的。
